# Дорожная карта ИИ-защитника v9.1

> **Целевая редакция:** максимальная эффективность и надёжность, долгосрочное развитие.
> **Статус:** исполняемая спецификация для старта проекта. Заменяет v9.0 (интеграция ревью: восстановлен контур автономного агента, уточнены метрики, добавлена операционная модель и сосуществование с EDR).
> **Платформы:** Windows 10/11/Server и Linux (systemd), десктоп + headless.
> **Вне области:** macOS, мобильные, runtime-контейнеры, коммерция/лицензирование (по решению владельца — позже).

**Изменения v9.1 (по ревью):**
1. Восстановлен контур автономного агента v6.x: second-agent review (разные модели, temperature=0), M7–M10, human spot-check, immutable guards, бюджет итераций, DEVLOG. Драйвер — уровень C, 100% PR через human-review.
2. Метрики E9/E10/E11 уточнены: prevalence-сценарий, привязка fast/slow, явный in-scope. Добавлена E12 (false block rate L0).
3. L0-операционка: бюджет allowlist, false block rate <0,1%, SLA разблокировки 4 ч, критерии перехода audit→enforce.
4. Драйвер — внешний критический путь (владелец, план B, дата решения); BSOD-метрики: canary-rate, halt при краше, фаззинг-бюджет.
5. Матрица eBPF/BTF/CONFIG_BPF_LSM с fallback auditd.
6. Операционная модель и сосуществование с EDR (Defender/CrowdStrike/SentinelOne).
7. ADR по TUI; обоснование весов интегральной метрики; сев-дефекты с recall ≥95%.

**Исключено (сознательно):** денежная оценка пилота (коммерция отложена — оставлена ресурсная оценка: ВМ и часы); полный чувствительный анализ весов (заменён нотой и проверкой на приёмке).

## 0. Паспорт документа

**Определения (единые для всего проекта):**

| Термин | Определение |
|---|---|
| **Надёжность** | доступность полной цепочки защиты, безотказность, сохранность данных, предсказуемость (fail-safe), устойчивость к враждебной среде |
| **Эффективность** | охват, TPR@FPR, MTTD, вероятность предотвращения, стоимость владения (FP/ресурсы/поддержка) |
| **ИИ-ядро** | когнитивный контур: видит все события, предлагает и направляет действия; НЕ является быстрым рефлексом |
| **Рефлекс** | детерминированный контур (ядро-компонент + правила + калиброванный ML), исполняет за <5 мс |
| **Обучение** | трёхъярусный цикл: локальная адаптация, локальная память кейсов, флотское обучение через сервер |
| **Алерт** | вердикт `severity ≥ medium`, требующий действия оператора/пользователя |

**Честные потолки (фиксируются, чтобы не обещать нереального):**
- 100% надёжности не бывает (обновления, ОС, железо, физический доступ).
- 100% эффективности против zero-day/кастомных целевых атак не даёт ни один вендор.
- «≥90%» — **интегральная** взвешенная метрика по классам угроз, а не «поймаем всё».

## 1. Видение и целевые показатели

**Видение.** Лёгкий EDR с ИИ-мозгом: двухконтурная архитектура (детерминированный рефлекс + когнитивный ИИ-советник), самообучающийся через флот — каждая отражённая атака делает следующую версию модели/правил/знаний лучше у всех. Ядро-компонент обеспечивает видимость и контроль, которые невозможны в user-mode.

### 1.1. Целевые показатели надёжности (R)

| # | Метрика | Цель |
|---|---|---|
| R1 | Доступность полной цепочки (full-fidelity) | ≥99,5% (стремимся к 99,9%) |
| R2 | Детекция тихого отказа источника | 100% за ≤60 с |
| R3 | MTTR после kill/отказа | p95 ≤30 с |
| R4 | Безотказность службы | ≥99,9% сессий без падений |
| R5 | BSOD по вине драйвера | 0 (canary: 0 за 2 недели) |
| R6 | Успех обновлений / откат | ≥99,9% / 100% |
| R7 | Отключение защиты пользователем из-за FP | <1%/мес |
| R8 | Потери событий (счётчики, не молча) | <0,01% |
| R9 | Fail-safe (необратимое без оператора) | 100% |
| R10 | Детекция тамперинга | 100%, с само-восстановлением |

### 1.2. Целевые показатели эффективности (E)

| # | Метрика | Цель |
|---|---|---|
| E1 | Предотвращение массовых угроз | ≥92% |
| E2 | Обнаружение массовых угроз | ≥95% |
| E3 | Обнаружение целевых угроз | ≥80% |
| E4 | Предотвращение целевых угроз | ≥70% |
| E5 | Fileless/LOLBin | ≥85% обн. / ≥75% пред. |
| E6 | Rootkit/kernel | ≥70% обн. / ≥60% пред. |
| E7 | TPR@FPR — файловые модели | ≥0,95 @ 0,05% FPR |
| E8 | TPR@FPR — поведение | ≥0,85 @ ≤1 алерт/2 нед |
| E9 | PPV | ≥50% при prevalence-сценарии (см. пояснения) |
| E10 | MTTD p95 / время сдерживания p95 | ≤1 с fast / ≤60 с slow / ≤5 с contain |
| E11 | Покрытие ATT&CK in-scope (обн/пред) | ≥90% / ≥70% |
| E12 | False block rate (L0 default-deny) | <0,1% в enforce; SLA разблокировки ≤4 ч |

**Методологические пояснения (как измерять честно):**
- **E9 (PPV)** зависит от базовой частоты угроз. Измеряем при явном prevalence-сценарии **«1 заражение на 1000 машин в месяц»**; если парк «чище» — отчитываемся TPR@FPR + alert budget, а не голым PPV (иначе цифра вводит в заблуждение).
- **E10 (fast/slow):** fast = процессы/файлы/сеть/креды (≤1 с); slow = агрегаты/корреляция/поведение за окно (≤60 с). Привязка fast/slow — к таблице окон взлома (§9).
- **E11 (in-scope):** все техники ATT&CK Enterprise, кроме firmware/hardware-level и физического доступа. Явный список + матрица «техника → слой → тест» в `docs/coverage-matrix.md`.
- **E12 (false block rate):** доля заблокированных L0, оказавшихся легитимными; измеряется в enforce-режиме; отдельно — SLA добавления в allowlist.

**Интегральная эффективность** `= 0,4·E1 + 0,2·E2 + 0,2·E3 + 0,1·E4 + 0,1·E11` → цель **≥90%**.
Веса отражают приоритет: предотвращение массовых (основной объём инцидентов) > обнаружение > целевые; покрытие — гигиенический фактор. **Проверка на приёмке:** при сдвиге любого веса ±0,1 интегральная метрика меняется <2 п.п. (иначе — пересмотр весов, `decision`).

### 1.3. Уровни поставки

| Контур | Описание | Потолок эффективности | Когда |
|---|---|---|---|
| **v9-min** | user-mode (нет ядро-подписи) | ~70–80% массовые, ~20–30% целевые | пока нет доступа к подписи |
| **v9-max** | ядро-компонент + контроль приложений | ≥90% (цель) | после получения подписи |
| **v9-ultra** (будущее) | + hardware root of trust, memory-forensics, XDR | →95%+ | долгосрочно |

## 2. Ключевые решения (ADR) с альтернативами

Каждое решение оформляется в `docs/adr/`, фиксируется `decision` в DEVLOG, имеет точку отката.

### D1. Ядро-компонент

| Вариант | Плюсы | Минусы | Рекомендация |
|---|---|---|---|
| A. Только user-mode | просто, нет BSOD-риска, нет подписи | нет памяти/ядра, потолок эффективности | **нет** (только как v9-min) |
| B. Minifilter+ELAM+ETW-TI / eBPF+LSM | видимость ядра, ранний запуск, нет логики в ядре | внешние зависимости (подпись, Microsoft-программа) | **ДА** |
| C. Вся логика в kernel-драйвере | максимум контроля | максимум BSOD-риска, огромная поверхность | **нет** |

**Триггер пересмотра:** недоступность attestation-подписи → временный v9-min (A), параллельно оформлять доступ.

### D2. Стек

| Вариант | Плюсы | Минусы | Рекомендация |
|---|---|---|---|
| Python везде | скорость разработки | GIL, RAM, старт, AV-флаги, слабее надёжность 99,5% | нет в runtime-пути |
| Rust ядро + Python tooling | память-безопасность, скорость, надёжность | порог входа | **ДА** |
| C++ ядро | производительность | ручное управление памятью, CVE-риск | запасной |

**Решение:** даемон, адаптеры, горячий путь, ML-инференс — Rust + ONNX Runtime; **CLI (`aidfctl`) — Rust** (hot-path для автоматизации); **TUI — Python/Textual** (отдельный процесс, не влияет на надёжность ядра, быстрая разработка). Python — обучение, анализ, скрипты. Драйвер Windows — минимальный C/Rust (только callbacks), eBPF — Rust (aya)/C + CO-RE. **Триггер:** если потребуется единый бинарь/меньший footprint → TUI переезжает на ratatui.

### D3. Контроль приложений (default-deny)

| ОС | Варианты | Рекомендация |
|---|---|---|
| Windows | WDAC / AppLocker / свой драйвер | **WDAC** (kernel-enforced deny-by-default); AppLocker — совместимость со старыми SKU |
| Linux | fapolicyd / IMA-appraisal / только SELinux | **fapolicyd + IMA** (audit → enforce поэтапно) |

**Действие:** audit-режим 2 недели → сформировать allowlist → enforce с dry-run, откатом и SLA разблокировки (см. §6.4).

### D4. Видимость на Linux

| Вариант | Рекомендация |
|---|---|
| auditd only | запасной |
| **eBPF (CO-RE)** | **ДА** (процессы/файлы/сеть/LSM-хуки), fallback auditd |
| kernel module | **нет** (подпись, обслуживание, риск) |

**Уточнение (матрица):** CO-RE требует BTF; LSM-eBPF требует `CONFIG_BPF_LSM` (kernel ≥5.7). Поддерживаемые конфигурации — §3.5; наличие BTF/CONFIG_BPF_LSM проверяется **в спайке**, а не предполагается. Без них — fallback auditd с деградацией метрик (фиксируется `degraded`).

### D5. Сетевая инспекция

| ОС | Варианты | Рекомендация |
|---|---|---|
| Windows | ETW+DNS / WFP callout / без сети | **WFP callout** (per-flow DPI, TLS-fp, DNS-filter); fallback ETW |
| Linux | nft cgroup / eBPF tc+XDP / conntrack-only | **eBPF tc/XDP**, fallback nft 5-tuple |

### D6. ИИ-архитектура

| Вариант | Плюсы | Минусы | Рекомендация |
|---|---|---|---|
| A. LLM как авторитетное ядро | «ИИ управляет всем» | недетерминизм, prompt-injection, латентность, неверифицируемо | **нет** |
| B. Двухконтурная (рефлекс + когнитивный ИИ) | ИИ видит всё и направляет; исполнение детерминировано | чуть больше архитектуры | **ДА** |
| C. Только ML, без LLM | просто | нет объяснений/триажа | запасной этап |

### D7. Обучение

| Вариант | Рекомендация |
|---|---|
| On-device fine-tune (градиенты) | **нет** (отравление, один пример не учит, невоспроизводимо) |
| **Флотское через сервер (3 яруса)** | **ДА** |
| Статично (без обучения) | нет, теряем ключевое преимущество |

### D8. LLM-модель

| Вариант | Рекомендация |
|---|---|
| 0,6B локально | запасной минимум |
| **1,7–4B локально** (Ollama) | **ДА** (качество/ресурс) |
| Облачный API | опционально, будущее/премиум, с согласием |

### D9. Персистентность

**Решение:** SQLite WAL + `BEGIN IMMEDIATE`; чувствительные поля — AES-GCM, ключ в ОС-хранилище (DPAPI / kernel keyring/TPM2). SQLCipher — опционально. RocksDB — только если упрёмся в производительность.

### D10. IPC

**Решение:** JSON-RPC 2.0; Windows named pipe (ACL + проверка токена), Linux `AF_UNIX SOCK_SEQPACKET` (`SO_PEERCRED`). gRPC/msgpack — только если гейт по латентности провален.

### D11. Упаковка и обновление

**Решение:** Windows MSI (WiX) с установкой службы; Linux deb+rpm + подписанный репозиторий. **Dual-slot A/B** обновления, canary-релиз (1% парка), автооткат по health-регрессии. MSIX/Flatpak/snap — **нет** для привилегированного демона.

### D12. Телеметрия наружу

**Решение:** opt-in, анонимизированная, self-hosted или облачный приёмник (отделяется от коммерции). Необходима для флотского обучения (ярус 2). Соблюдение 152-ФЗ/GDPR: согласие, минимизация, удаление.

### D13. Сосуществование с EDR/AV

**Решение:** работаем **рядом** с Defender/CrowdStrike/SentinelOne, не «вместо». Ядро-компонент проектируется с расчётом на сосуществование (минимальный набор callbacks, отсутствие конкурирующих перехватов), обязательные тесты на машинах с топ-3 EDR (§14). При конфликте — режим `compat` (только наблюдение, без перехвата), а не отключение.

## 3. Архитектура

### 3.1. Слои L0–L8

```
L0 Предотвращение:  WDAC/fapolicyd+IMA, protected folders, Exploit Protection
L1 Ядро-видимость:  minifilter+ELAM+ETW-TI  |  eBPF/LSM+auditd+fanotify
L2 Инспекция запуска: AMSI, script logging  |  LSM bprm, интерпретаторы
L3 Память/эксплойты: LSASS protection, anti-injection, memory scan | kprobe, /proc/mem
L4 Сеть:            WFP callout (DPI,TLS-fp,DNS) | eBPF tc/XDP, nft, DNS
L5 Реагирование:    kernel suspend/quarantine/rollback + canary + deception
L6 Детекция:        правила + ML-ансамбль (файл/поведение/память/сеть)
L7 Надёжность:      heartbeat, проб, overflow-free, dual-slot, self-heal
L8 Самозащита:      тампер-доказательность, PPL/IMA, fs-verity, ключи вне агента
```

### 3.2. Двухконтурный ИИ

```
КОГНИТИВНЫЙ контур (ИИ, 1–10 с)         РЕФЛЕКС (детерминированный, <5 мс)
  полное восприятие событий               ядро-компонент (driver/eBPF)
  корреляция, гипотезы, приоритеты        политика + правила
  предложение: изолировать дерево X,      калиброванные ML-скоры (ONNX)
  объяснить, оценить                       обратимые действия: suspend/block/quarantine
          │                                       ▲
          └──► ПОЛИТИЧЕСКИЙ ГЕЙТ ─────────────────┘
               (allowlist действий, обратимые-первыми,
                порог уверенности, human-approval
                для необратимого)
```

ИИ имеет полное восприятие и право направлять; исполнение — через узкий детерминированный слой, который работает всегда, даже если ИИ упал.

## 4. Контракты и модель данных v3.0

Схемы `schemas/v3/` (Pydantic + JSON Schema). `3.x` — обратно совместимые дополнения, `4.0` — ломающие. Ядро принимает `3.x`, отклоняет `4.0` с `incompatible_schema`.

```python
class Event(BaseModel):
    schema_version: Literal["3.0"]
    event_id: UUID
    trace_id: UUID
    ts_event: datetime          # время источника
    ts_ingest: datetime         # время чтения
    platform: Literal["windows", "linux"]
    source: str                 # "win.etw.ti", "linux.ebpf", "win.amsi", ...
    layer: str                  # "kernel" | "user" | "script" | "network" | "memory"
    category: EventCategory
    action: str
    actor: Actor | None
    object: ObjectRef | None
    user: UserRef | None
    host: HostInfo
    integrity: IntegrityInfo | None
    raw_ref: str
    pii: PiiFlags
    platform_data: dict[str, Any]
    kernel_meta: KernelMeta | None  # callback context, irql, trust
```

Дополнительные контракты: `Verdict`, `Action`, `Confirmation`, `Health`, `ModuleManifest`, `PlatformCapabilities`, **`CaseMemoryEntry`** (ярус 1 обучения), **`ModelPack`** (манифест+подпись+регрессия), **`LearningUpdate`** (ярус 2: правила/веса/Q&A/task-solution).

Правила версионирования: SemVer для продукта и схем отдельно; `min_core_version`; capability negotiation.

## 5. Надёжность ≥99,5%

### 5.1. Ошибка бюджета

99,5% = 3,65 ч/мес downtime; 99,9% = 43,8 мин/мес. Распределение: обновления ≤15 мин/мес, деградации ≤60 мин/мес, инциденты ≤90 мин/мес. При превышении — freeze фич, только стабилизация.

### 5.2. Механизмы (обязательные)

| # | Механизм | Закрывает |
|---|---|---|
| 1 | Heartbeat каждого источника + синтетическая проба каждые 60 с | тихая смерть ETW/auditd/fanotify/eBPF |
| 2 | Счётчики потерь (`lost`, overflow, backlog) + алерт при >0 | silent event loss |
| 3 | Overflow-free ingest: приоритеты (процесс/учётка > файлы > auth-шум), агрегация, резерв, никогда молча не дропать | шторм событий |
| 4 | Dual-slot A/B + canary-релиз + автооткат по health | «кирпич» |
| 5 | Watchdog×2 (SCM+supervisor / systemd+supervisor) + backoff + circuit breaker | crash loop |
| 6 | Safe mode + last-known-good конфиг + dry-run правил/моделей | плохой релиз/конфиг |
| 7 | Драйвер: только callbacks, фаззинг, статика, WHQL/attestation, консервативный откат | BSOD |
| 8 | Данные: WAL+checksum+backup, отказ от сетевых путей, квота+резервация диска, fsync | потеря/порча |
| 9 | Монотонные часы + детекция скачка времени; часовой re-check прав | корреляция, дрейф прав |
| 10 | Fail-safe: таймаут=отказ; T3 без оператора — очередь | необратимый ущерб |

### 5.3. FMEA — главные риски

| Отказ | Митигация |
|---|---|
| Шторм событий → переполнение | приоритеты + агрегация + резерв |
| Тихая смерть источника | heartbeat + проба |
| Дрейф прав после обновления ОС/SELinux | re-check + алерт + само-восстановление |
| Переполнение inotify/RDCW | `IN_Q_OVERFLOW`/`ERROR_NOTIFY_ENUM_DIR` → rescan по USN/full |
| Конфликт с Defender/AV | EV-подпись, тесты на матрице, ранняя проверка |
| FP → пользователь отключает | бюджет алертов, suppression, allowlist |

## 6. Эффективность ≥90%

**Принцип:** 90%+ достигается слоями L0–L5, а не «лучшим ML». L0 (default-deny) — главный рычаг: неизвестный бинарь не исполняется. L6 (ML) даёт детекцию неизвестного и адаптацию.

### 6.1. Механизмы по слоям

| Слой | Windows | Linux | Ловит |
|---|---|---|---|
| L0 | WDAC, protected folders, Exploit Protection | fapolicyd+IMA, noexec | 90%+ массовых на исполнении |
| L1 | minifilter, ELAM, ETW-TI | eBPF/LSM, auditd | цепочки, инъекции, ранний запуск |
| L2 | AMSI, script logging, CLR | LSM bprm, интерпретаторы | обфусцированные скрипты |
| L3 | LSASS protection, anti-injection, memory scan | kprobe, /proc/mem | fileless, дампы |
| L4 | WFP callout, DNS, TLS-fp | eBPF tc/XDP, nft, DNS | C2, exfil, DoH |
| L5 | kernel suspend/quarantine/rollback, canary, deception | ← те же | сдерживание ≤5 с |
| L6 | ML-ансамбль | ML-ансамбль | неизвестное, варианты |

### 6.2. Борьба с базовой ставкой (почему алерты врут)

При 1 алерте/день и ~5 инцидентах/год PPV ≈ 4% — пользователь тонет в шуме. Поэтому: **бюджет ≤1 medium+ алерт на хост в 1–2 недели**, suppression, allowlist, и **PPV ≥50%** (при prevalence-сценарии, §1.2). Поведенческая модель отчитывается TPR@FPR, а не «1 алерт/день».

### 6.3. Инкремент над Defender

На Windows Defender ловит 95%+ массовых. Эффективность мерить как **прирост над Defender** (иначе цифры врут): +1–5 п.п. массовые, +10–20 п.п. ransomware-поведение/LOLBin. На Linux базовой AV нет — абсолютная ценность выше, но и телеметрия сложнее.

### 6.4. Операционная цена L0 (default-deny) — обязательный контур

WDAC/fapolicyd в enforce дают сотни ложных блокировок легитимного в первые недели. Без управления этим «≥90% предотвращения» превращается в «≥90% блокировки легитимного», и продукт отключают за месяц. Обязательно:

| Элемент | Требование |
|---|---|
| Allowlist-инженерия | выделенный владелец + время в плане пилота (не «само сложится») |
| False block rate | <0,1% в enforce (E12), мониторится ежедневно |
| SLA разблокировки | добавление в allowlist ≤4 ч с момента инцидента |
| Переход audit→enforce | критерии: 2 недели audit без критичных блоков + allowlist покрывает ≥99,5% наблюдаемого легитимного |
| Откат | политика L0 откатывается одним действием (kill-switch) без переустановки |

Принцип v6.x сохранён: **FP дороже пропусков на ранних этапах** — здесь он главный.

## 7. ИИ-ядро и управление

### 7.1. Уровни автономии

| Уровень | Что может | Контроль |
|---|---|---|
| Reflex (автономный) | обратимые действия (suspend/block/quarantine) по политике+скору | детерминированный гейт |
| Cognitive-propose | предлагает план сдерживания, объяснение, приоритет | гейт + human-approval для необратимого |
| Cognitive-act (растёт по данным) | автоматизация всё большего числа обратимых действий | по метрикам PPV/FP/time-to-contain |
| Never | необратимое (terminate/delete) без подтверждения; изменение политики/модели угроз | всегда human |

### 7.2. Защита от prompt-injection

- LLM читает только **нормализованные события**, а не сырой контент; пути/командные строки — ред актированы.
- LLM **не имеет** авторитета исполнения: его вывод — это *предложение*, проходящее гейт.
- Промпты и few-shot-примеры — только из доверенного подписанного источника.
- Все действия LLM логируются и откатываемы.

### 7.3. Рост автономии данными, а не обещанием

Автономия когнитивного контура повышается **только** когда PPV≥50%, FP в бюджете, время сдерживания p95≤5 с стабильно на протяжении N недель. Это фиксируется метриками и `decision`, не субъективно.

## 8. Цикл самообучения (learning loop)

Три яруса. Градиенты на устройстве — запрещены (`MODELS_TRAIN_ON_DEVICE = False`, immutable).

### 8.1. Ярус 0 — локальная адаптация (без весов)

Baseline-статистика, калибровка порогов, локальный allowlist (пользователь дважды разрешил → запомнили), per-process-репутация. Обратимо, сбрасываемо (`baseline reset`).

### 8.2. Ярус 1 — память подтверждённых кейсов

Когда атака подтверждена (правило, аналитик, песочница, согласие ансамбля, threat-intel — **не** самовывод модели), добавляется `CaseMemoryEntry` (вектор признаков + вердикт + контекст). Retrieval (k-NN/сходство) даёт мгновенное распознавание вариантов уже виденных атак. Память: подписанная, ограниченная по объёму, откатываемая.

### 8.3. Ярус 2 — флотское обучение через сервер

```
атака → подтверждение → анонимизированная телеметрия (opt-in)
  → сервер: курирование, разметка, детонация в песочнице
  → офлайн-дообучение (LoRA/тонкая настройка) + новые правила
    + пары «вопрос→ответ» + «задача→решение»
  → регрессия (TPR@FPR, FP-бюджет), подпись, версия
  → подписанное обновление на устройства
```

### 8.4. «Вопрос→ответ» и «задача→решение»

| Формат | Пример | Использование |
|---|---|---|
| вопрос→ответ | «что значит 4625×N?» → объяснение | RAG-база, `kb_version` |
| задача→решение (few-shot) | «процесс X из /tmp лезет в сеть» → «изолировать+объяснить» | контекст LLM при инференсе |
| задача→решение (обучающий набор) | накопленные пары | офлайн-тонкая настройка |

LoRA-адаптеры: сервер обучает под среду/отрасль, подписывает, шлёт; на устройстве — только инференс.

### 8.5. Защита от отравления

Подтверждение — доверенные источники; телеметрия валидируется на сервере; дообучение — изолированная ВМ + replay-буфер (защита от забывания); обновление проходит FP-бюджет и регрессию; подпись + версия + откат + kill-switch.

### 8.6. Метрики «реально учится»

Растёт: обнаружение новых вариантов, TPR на свежем holdout. Падает: MTTD, время сдерживания. Не растёт: FP-бюджет, откаты обновлений.

## 10. Самозащита, безопасность поставки и контур автономного агента

### 10.1. Самозащита

| Механизм | Windows | Linux |
|---|---|---|
| Тампер-доказательность | ETW+Event Log, подпись, ACL | append-only журнал, auditd, fs-verity |
| Защита процесса | PPL (через драйвер), ELAM | systemd hardening, IMA, AppArmor/SELinux |
| Целостность | Authenticode+каталог, Ed25519-манифест | GPG+fs-verity+IMA |
| Ключи | HSM/CI-secret вне агента | HSM/TPM вне агента |
| Обновление | dual-slot, canary, откат | dual-slot, canary, откат |

### 10.2. Trust boundary (гейты вне периметра агента)

Главное правило v6.x, восстановлено и усилено для драйвера: **агент не запускает и не редактирует проверки, которые его оценивают.**

- Защищённая ветка, CODEOWNERS, обязательный human-review через API платформы; `human_acceptance` — подписанный коммит человека из allowlist, а не строка в коммите.
- Авто-ревьюер — отдельный CI-workflow на protected branch; автор не может его редактировать; вердикт и `run_id` фиксирует CI.
- Ключи подписи (драйвер/модели/обновления) — HSM/CI-secret, недоступны агенту.
- Драйвер/ядро-компонент — отдельный репозиторий со строжайшим ревью; **любое изменение — только с human-подписью**.

### 10.3. Уровни автономии разработки

| Уровень | Что можно | Контроль |
|---|---|---|
| A | код модулей, тесты, документация, конфиги | CI + авто-ревьюер + тесты |
| B | `core/`, `rules/`, `response/`, `watchdog/`, адаптеры, схемы | second-agent review + CI + метрики |
| **C** | **драйвер/ядро-компонент, модель угроз, политика fail-safe, метрики, обновление моделей** | **только human-подпись, без исключений** |

### 10.4. Second-agent review (авто-ревьюер)

- Изоляция ролей: `reviewer_run_id != author_run_id` **И** `reviewer_model != author_model` **И** `reviewer_prompt != author_prompt` **И** `reviewer_temperature == 0`. Иначе вердикт недействителен → escalate.
- Проверки: diff vs контракт; immutable-чек; capability negotiation; перепрогон тестов (не доверять «зелёному» CI); покрытие (новое ≥80%, изменённое ≥60%); тесты-пустышки (`assert` без проверки, `pass`, `try/except: pass`); TODO/FIXME в критичных модулях; мутационное тестирование (выживание ≤20%); **нет `fit`/`train` в runtime**; M/E/R-метрики не изменены.
- Вердикт: `approve` / `request_changes` / `escalate`.

### 10.5. Human spot-check и сев-дефекты

- **M9:** случайная выборка одобренных PR + **100% PR драйвера/ядро-компонента**; дефекты → DEVLOG `spot_check`.
- **Сев-дефекты (seeded defects):** в выборку намеренно внедряются дефекты; измеряется **recall ревьюера ≥95%** (ловит ≥95% сев-дефектов). Это калибровка ревьюера, а не только модульное тестирование.

### 10.6. Immutable guards (`core/policy.py`, CI блокирует merge без human-подписи)

```python
# IMMUTABLE: requires human_acceptance
FAIL_SAFE_ON_TIMEOUT = "reject"        # НИКОГДА не "accept"
MODELS_TRAIN_ON_DEVICE = False         # НИКОГДА не True
DRIVER_SIGNED_BY_HUMAN = True          # НИКОГДА не False
KERNEL_CODE_REVIEW_REQUIRED = True     # НИКОГДА не False
```

### 10.7. Бюджет итераций и эскалация

На подэтап — лимит 5 итераций «код → тест → фикс». Исчерпан → эскалация человеку (SLA 48 ч, список заместителей). Стоп-условия: изменение immutable; драйвер без human-подписи; авто-ревьюер и автор не сошлись за 3 раунда; любой BSOD; `tamper`/инцидент без объяснения; M9 >5%; M8 вне коридора; попытка `fit`/`train` в runtime.

### 10.8. DEVLOG

Типы: `code`, `test`, `decision`, `incident`, `tamper`, `auto_review`, `escalation`, `spot_check`, `model_update`, `driver_review`. Обязательные поля: `actor` (agent / agent+auto_review / agent+human_acceptance / human), `run_id`, `auto_review`, `human_acceptance` (для C), доказательства — артефакты CI. Правило: «код → проверка → журнал»; без проверки — `unverified`.

### 10.9. Метрики качества (Q)

| # | Метрика | Цель |
|---|---|---|
| M7 | «Зелёные» тесты, прошедшие повторный прогон ревьюера | ≥95% |
| M8 | Доля PR, отклонённых ревьюером | 10–30% (окно 8 недель, p-карта) |
| M9 | Проблемы в одобренных PR (spot-check) | ≤5% (накопленная выборка ≥59) |
| M10 | Изменения драйвера с human-review до merge | 100% |
| Q-seed | Recall ревьюера на сев-дефектах | ≥95% |

### 10.10. SBOM и безопасность поставки

SBOM, lock-файлы с хешами, `cargo audit`/`pip-audit`, воспроизводимые сборки MSI/deb/rpm, политика раскрытия уязвимостей, bug bounty.

## 13. Долгосрочное развитие (горизонты)

- **Ближний (после релиза):** тюнинг suppression/allowlist, фиды (hash reputation, Sigma), расширение deception, калибровка PPV.
- **Средний:** network DPI + TLS-инспекция (opt-in MITM), авто-переобучение офлайн, облачная корреляция (opt-in), threat intel, memory-forensics.
- **Дальний:** hardware root of trust (TPM/measured boot), Trusted Boot, глубже eBPF-руткит-детекция, XDR-интеграция, self-supervised ML, формальная верификация драйвера.

**Точки расширения:** плагин-интерфейс детекторов/реакций, реестр моделей (shadow/canary), интеллект-коннекторы, OTel-телеметрия, версионируемые схемы + capability negotiation, API и конфиг-миграции без breaking.

## 14. Операционная модель и сосуществование

### 14.1. Владельцы и роли

| Роль | Ответственность |
|---|---|
| PM | внешний критический путь (подпись), решения v9-min/v9-max, приёмка |
| Security engineer (человек) | human-review драйвера (100% PR), spot-check, red-team, эскалации |
| Allowlist-куратор | L0: allowlist, разблокировка ≤4 ч, false block rate |
| Оператор клиента | установка, инциденты, обновления (в пилоте — мы) |

### 14.2. Сосуществование с EDR/AV

Ядро-компонент (minifilter+ELAM / eBPF) может конфликтовать с Defender/CrowdStrike/SentinelOne — это реальная причина BSOD и отказов. Поэтому:

- Режим `compat`: только наблюдение (без перехвата), если обнаружен конкурирующий драйвер/EDR.
- Тесты на машинах с топ-3 EDR — в матрице (§12).
- Приоритет: **не ломать чужую защиту**, а дополнять; при конфликте — деградация, не борьба.

### 14.3. Ресурсы пилота (без денежной оценки)

- ВМ: Windows 10/11/Server ×2, Ubuntu/Debian/RHEL/Fedora ×2, машины с топ-3 EDR ×3.
- Red-team: 20 сценариев/ОС, ~2 человеко-недели на платформу на прогон.
- Human-review драйвера: закладывается в план, а не «по мере».
