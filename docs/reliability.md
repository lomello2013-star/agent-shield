# Надёжностный контур

> **Статус:** норматив. Разворачивает v9.1 §5.
> **Цель:** доступность полной цепочки ≥99,5% (стремимся к 99,9%), 0 BSOD, 0 тихих отказов, 100% откат обновлений.

## 1. Метрики R1–R10

| # | Метрика | Цель | Метод измерения |
|---|---|---|---|
| R1 | Доступность full-fidelity | ≥99,5% (→99,9%) | время с полным стеком / uptime ОС |
| R2 | Детекция тихого отказа источника | 100% за ≤60 с | heartbeat + синтетическая проба каждые 60 с |
| R3 | MTTR после kill/отказа | p95 ≤30 с | fault-injection тесты |
| R4 | Безотказность службы | ≥99,9% сессий без падений | телеметрия крашей |
| R5 | BSOD по вине драйвера | 0 | WER/ETW, canary-парк |
| R6 | Успех обновлений / откат | ≥99,9% / 100% | staged-тесты |
| R7 | Отключение из-за FP | <1%/мес | пилот-телеметрия |
| R8 | Потери событий | <0,01% | счётчики `lost`/overflow/backlog |
| R9 | Fail-safe | 100% | симуляция без оператора |
| R10 | Детекция тамперинга | 100%, само-восстановление | tamper-тесты |

## 2. Error budget

- 99,5% = 3,65 ч/мес; 99,9% = 43,8 мин/мес.
- Распределение: обновления ≤15 мин/мес, деградации ≤60 мин/мес, инциденты ≤90 мин/мес.
- Превышение → freeze фич, только стабилизация (зафиксировано в политике).

## 3. Механизмы (обязательные)

| # | Механизм | Что делает | Проверка |
|---|---|---|---|
| 1 | Heartbeat + синтетическая проба | каждые 60 с пробное событие/файл на каждый источник | проба не пришла → `incident` |
| 2 | Счётчики потерь | `lost`, overflow, backlog на источник; алерт при >0 | 0 незаметных дропов |
| 3 | Overflow-free ingest | приоритеты (процесс/учётка > файлы > auth-шум), агрегация, резерв ёмкости, никогда молча не дропать | шторм-тест |
| 4 | Dual-slot A/B + canary-релиз | 1% парка → 10% → 100%; автооткат по health | откат-тест |
| 5 | Watchdog×2 + backoff + circuit breaker | SCM+supervisor / systemd+supervisor; экспоненциальный backoff | kill-тест |
| 6 | Safe mode + last-known-good + dry-run | конфиг/правила/модели валидируются до применения | bad-config тест |
| 7 | Драйвер: callbacks + фаззинг + статика | никакого парсинга в ядре, фаззинг 10k/ночь | BSOD-тест |
| 8 | Данные: WAL+checksum+backup | отказ сетевых путей, квота+резервация, fsync | kill -9 тест |
| 9 | Монотонные часы + re-check прав | детекция скачка времени; часовой re-check | clock-jump тест |
| 10 | Fail-safe | таймаут=отказ; T3 без оператора — очередь | симуляция |

## 5. Тихие отказы — приоритет №1

«Тихая смерть» выглядит как «всё хорошо». Механизмы детекции:

- **Windows:** ETW-сессия потеряна (переполнение буфера) → heartbeat; `ReadDirectoryChangesW` вернул `ERROR_NOTIFY_ENUM_DIR` → rescan по USN.
- **Linux:** inotify `IN_Q_OVERFLOW`; fanotify переполнение очереди; auditd `lost`; после перезапуска auditd правила могли не примениться → re-check.
- **Оба:** после обновления ОС/SELinux изменились политики/ACL → часовой re-check + проба.

Правило: любая потеря/деградация — это событие `incident`, а не тихий счётчик.

## 6. Деградации

| Отсутствует | Поведение |
|---|---|
| Sysmon (Win) | ETW + Security Log; полнота behavior ниже, F1 фиксируется отдельно |
| ETW-сессия | Security Log + polling; `degraded`, M1b растёт |
| auditd (Linux) | eBPF → journald; без обоих — `degraded`, только файлы |
| eBPF/BTF | auditd + fanotify; урезанный набор признаков |
| fanotify | inotify с рекурсивными watch |
| cgroup v2/nft | 5-tuple блок, пометка best-effort |
| systemd | foreground + sysv, без watchdog (`degraded`) |

Каждая деградация — `health.degraded` с причиной и записью в диагностику.

## 7. Восстановление и MTTR

- Watchdog перезапускает демон за ≤5 с (Windows) / ≤3 с (systemd).
- Backoff: 0→1→2→4→8 с → кап; circuit breaker против crash loop.
- `failed`-состояние модуля сохраняется до ручного сброса (не «само вылечивается»).
- Незавершённые подтверждения при kill → в аудит (не выполняем). Outbox — идемпотентная досылка.

## 8. Драйвер: BSOD-инженерия

| Метрика | Цель |
|---|---|
| BSOD-rate на canary (1%) | 0 за 2 недели до раскатки |
| Телеметрия крашей | WER/ETW; halt раскатки при любом BSOD |
| Фаззинг | 10k итераций/ночь, 0 крашей, с покрытием |
| Статический анализ | 0 критичных (clang-analyzer/CodeQL/miri) |
| Принцип | только callbacks, никакого парсинга в ядре; минимальный объём |

## 9. Обновление и откат (dual-slot)

- A/B два слота; обновление пишется в неактивный слот → переключение атомарно.
- Canary-релиз: 1% → 10% → 100%; на каждом шаге мониторинг health/FP/BSOD.
- Автооткат при регрессии; ручной откат одной командой.
- Kill-switch на правило/модель/драйвер по id.
- Откат-тест обязателен: «обновили → регрессия → откат → состояние идентично».

## 10. Целостность данных

- SQLite WAL + `BEGIN IMMEDIATE` + checksum; отказ от сетевых путей (иначе отказ установки).
- Дисковая резервация (10%) + квота + LRU-эвикция + алерт.
- fsync-дисциплина на критичных записях; backup перед миграцией схемы.
- Чувствительные поля — AES-GCM, ключ в ОС-хранилище.

## 11. Chaos-тестирование

Обязательные сценарии перед релизом: kill источника/демона/парсера, заполнение диска, скачок часов, отзыв прав, обрыв сети, порча БД, переполнение очереди, конфликт с EDR, BSOD-симуляция. Критерий: R2/R3/R5/R6/R8/R9 в целях, 0 потерь данных.
