# Реестр архитектурных решений (ADR)

> **Статус:** норматив. Раскрывает v9.1 §2. Каждое решение — в отдельной записи; при изменении — новая версия записи, старая сохраняется с пометкой `superseded`.

Формат записи: **Контекст → Варианты → Решение → Последствия → Когда пересмотреть.**

## D1. Ядро-компонент

- **Контекст:** потолок user-mode ~70–80% массовые; 90%+ требует видимости/контроля ядра.
- **Варианты:** A user-mode only; B minifilter+ELAM+ETW-TI / eBPF+LSM; C вся логика в драйвере.
- **Решение:** B. Логика вне ядра, ядро — только callbacks.
- **Последствия:** внешние зависимости (подпись, Microsoft-программа), BSOD-поверхность → отдельный контур (§reliability).
- **Пересмотр:** недоступность подписи → v9-min (A), параллельно оформлять доступ.

## D2. Стек

- **Решение:** Rust (демон, адаптеры, ML-инференс, CLI) + Python (обучение/скрипты) + Textual (TUI). Драйвер — C/Rust; eBPF — Rust (aya)/C.
- **Последствия:** память-безопасность, надёжность; порог входа выше.
- **Пересмотр:** нет Rust-компетенций → C++/Go; нужен единый бинарь → TUI на ratatui.

## D3. Контроль приложений (default-deny)

- **Решение:** Windows WDAC; Linux fapolicyd+IMA. audit → allowlist → enforce с dry-run и откатом.
- **Последствия:** E12 false block rate <0,1%, SLA разблокировки ≤4 ч (см. operations.md).
- **Пересмотр:** конфликт с корпоративными политиками → режим дополнения.

## D4. Видимость на Linux

- **Решение:** eBPF (CO-RE) с fallback auditd. Kernel module — нет.
- **Последствия:** нужны BTF и CONFIG_BPF_LSM (проверка в спайке), иначе `degraded`.
- **Пересмотр:** нет BTF на целевых ядрах → auditd-контур.

## D5. Сетевая инспекция

- **Решение:** Windows WFP callout; Linux eBPF tc/XDP. Fallback: ETW / nft 5-tuple.
- **Пересмотр:** проблемы с WFP callout → ETW-only; eBPF недоступен → nft.

## D6. ИИ-архитектура

- **Решение:** двухконтурная (детерминированный рефлекс + когнитивный ИИ-советник через политический гейт).
- **Последствия:** prompt-injection не даёт прямого управления (§ai-governance).
- **Пересмотр:** нет (A «LLM как авторитетное ядро» отклонён из-за недетерминизма/инъекций).

## D7. Обучение

- **Решение:** 3 яруса (локальная адаптация, память кейсов, флотское обучение через сервер). Градиенты на устройстве запрещены.
- **Пересмотр:** нет (on-device fine-tune отклонён: отравление, невоспроизводимость).

## D8. LLM-модель

- **Решение:** 1,7–4B локально (Ollama); 0,6B — запасной; облако — опционально.
- **Пересмотр:** качество объяснений ниже цели → крупнее модель или шаблоны.

## D9. Персистентность

- **Решение:** SQLite WAL + AES-GCM для чувствительных полей (ключ в DPAPI/keyring/TPM). SQLCipher/RocksDB — опционально.
- **Пересмотр:** производительность → RocksDB; полное шифрование → SQLCipher.

## D10. IPC

- **Решение:** JSON-RPC 2.0; named pipe (Windows) / AF_UNIX SOCK_SEQPACKET (Linux).
- **Пересмотр:** гейт латентности провален → gRPC/msgpack.

## D11. Упаковка и обновление

- **Решение:** MSI (WiX) / deb+rpm; dual-slot A/B; canary-релиз; автооткат.
- **Пересмотр:** требования к бесшовности → MSIX (с оговоркой про службу).

## D12. Телеметрия наружу

- **Решение:** opt-in, анонимизированная, self-hosted/облако; для флотского обучения.
- **Последствия:** 152-ФЗ/GDPR (согласие, минимизация, удаление).

## D13. Сосуществование с EDR/AV

- **Решение:** работаем рядом (не вместо); режим `compat` при конфликте; тесты с топ-3 EDR.
- **Пересмотр:** конфликт неустраним → только наблюдение (без перехвата).

## D14. Multi-tenant (STML)

- **Статус:** черновик (финализация в S8, решение о необходимости — в S1).
- **Решение:** single-tenant MVP; `tenant_id` в схеме с S0; при >1 клиенте/регуляторном требовании — RLS (≤10) → schema-per-tenant/отдельные кластеры (>10).
- **Пересмотр:** «>10 тенантов» — измерить RLS-производительность, а не считать порогом необходимости.

## D15. Транспорт коннектора: pickle → JSON (STML)

- **Статус:** черновик (решение в S0.0c).
- **Решение:** Python-клиент к `core/ipc.py` (pickle) + внутренний JSON-RPC на `127.0.0.1:port`; динамический порт + lock-файл PID + hash бинарника; при занятости — `degraded`, не тихий fallback. JSON-RPC — часть контракта коннектора, версионируется вместе с `stml/v0`.
- **Отклонено:** второй прослушиватель агента на HTTP-порт (изменяет ядро агента).

## D16. Event bus: outbox → NATS → Kafka (STML)

- **Статус:** черновик (решение до старта S5).
- **Решение:** Postgres outbox (MVP) → NATS JetStream (>1k) → Kafka (если уже есть кластер/нужна партиционная модель). Postgres outbox не является fallback при >1k — при нестабильности NATS остановка масштабирования.

---

**Правило:** любое решение, влияющее на надёжность/эффективность/безопасность, фиксируется ADR до реализации; отклонение от ADR без новой записи — блокируется на ревью.
