# Этапы и порядок старта

> **Статус:** норматив. Раскрывает v9.1 §11 и §16. Сроки не фиксируются — только фазовые гейты.

## 1. Этапы (гейты выхода)

| Этап | Содержание | Гейт выхода |
|---|---|---|
| **0. Спайки** | ядро-подпись, WDAC/fapolicyd, AMSI/ETW-TI, eBPF (BTF/LSM), драйвер-стабильность, ML на свежих данных, сеть | измерены 7 спайков, `decision` по стеку/потолку |
| **1. Надёжностная платформа** | R1–R10: heartbeat, проба, overflow-free, dual-slot, watchdog×2, safe mode | R2/R4/R6 в целях; fault-injection без потерь |
| **2. Контроль приложений** | WDAC, protected folders / fapolicyd+IMA, noexec | E1 ≥90%, E12 <0,1% в audit→enforce |
| **3. Ядро-видимость** | minifilter+ELAM+ETW-TI / eBPF+LSM+auditd+fanotify | события ядра в `Event v3.0`, 0 BSOD |
| **4. Телеметрия full-fidelity** | нормализация, приоритетные очереди, retention/PII | R8, потери <0,01% |
| **5. Детекция и покрытие** | правила + coverage harness + скрытый holdout | E11 ≥90% обн; TPR на holdout |
| **6. Инспекция исполнения** | AMSI, script logging / LSM bprm | E5 ≥85% |
| **7. Реагирование** | kernel suspend/quarantine/rollback, canary, deception | E10 ≤5 с; откат 100% |
| **8. ML-ансамбль** | PE/ELF/script/behavior/memory/net, shadow deploy | E7/E8; регрессия моделей |
| **9. Память/креды** | LSASS protection, anti-injection / kprobe, canary-креды | E3 ≥80% на дамп-техниках |
| **10. Сетевая инспекция** | WFP callout / eBPF tc/XDP, DNS, TLS-fp | E4 ≥70%; C2-сценарии |
| **11. Самозащита** | PPL, ELAM / IMA, fs-verity, SELinux | R10; тампер → `tamper` 100% |
| **12. Упрочнение и релиз** | soak, fuzz, red-team 20/ОС, матрица | R/E/Q-метрики в целях; `human_acceptance` |

**Зависимости:** 2→3→4→5→7 последовательны; 1, 8, 11 — параллельно; 0 — до всего.

## 2. Внешний критический путь: подпись драйвера

Microsoft attestation + ELAM — многомесячный процесс (EV, Hardware Dev Center, проверка кода, WHQL, политика обновлений; ELAM — отдельный договор).

| Элемент | Требование |
|---|---|
| Владелец | PM (не агент) |
| Дата решения | зафиксировать до старта этапа 3 |
| План B | v9-min (user-mode) как временный |
| Бесшовность | код готов к переходу v9-min → v9-max |

## 3. BSOD — количественная цель драйвера

| Метрика | Цель |
|---|---|
| BSOD-rate canary (1%) | 0 за 2 недели |
| Телеметрия | WER/ETW; halt раскатки при BSOD |
| Фаззинг | 10k/ночь, 0 крашей |
| Статика | 0 критичных |

## 4. Порядок старта (первые действия)

1. Зафиксировать карту v9.1 как baseline; завести ADR D1–D13.
2. Запустить внешний критический путь (подпись).
3. Спайки этапа 0; записать измерения, утвердить потолки и матрицу ядер.
4. Надёжностная платформа (R1–R10) **до** любого детектора.
5. Контроль приложений (L0) с allowlist/SLA/E12.
6. Ядро-видимость (L1) → телеметрия → детекция → реагирование.
7. Параллельно: самозащита (L8), ML (L6), цикл обучения (ярус 1 и 2), контур агента.
8. Red-team после каждого слоя; корректировать цели и реестр окон.

## 5. Чек-лист готовности к старту

- [ ] Подтверждены потолки и матрица ядер (спайки).
- [ ] Надёжностная платформа: heartbeat, проба, счётчики, dual-slot, watchdog×2, safe mode.
- [ ] Контроль приложений в audit + allowlist-контур + SLA.
- [ ] Ядро-компонент подписан и стабилен (0 BSOD).
- [ ] Схемы v3.0 + capability negotiation.
- [ ] Контур агента: гейты вне периметра, драйвер=уровень C, immutable, M10=100%.
- [ ] Цикл обучения: ярус 1 + ярус 2 (сервер + Q&A/task-solution).
